# Architecture

Morse Runner for macOS is a Swift package (`Swift/Package.swift`) plus an
AppKit app (`Swift/App`, generated by xcodegen from `Swift/project.yml`).

```
+-----------------------------------------------------+
| App (AppKit)   window, menus, custom-drawn widgets   |
|                EngineBridge: commands in, events out |
+-----------------------------------------------------+
| MRAppCore      keys, Enter-sends-message, Run rules, |
|                captions, end-of-contest, score files |
+-----------------------------------------------------+
| MRAudio        AVAudioEngine output, SPSC block ring,|
|                simulation thread                     |
| MRSimulation   Contest, stations, DX operator FSM,   |
|                Master.dta                            |
| MRScoring      QSO log, prefixes, HST points, CRC32  |
| MRPersistence  settings (UserDefaults)               |
+-----------------------------------------------------+
| MRDSP          keyer, filters, modulator, AGC, QSB   |
| MRCore         constants, Delphi rounding, MT19937,  |
|                byte strings, WAV writer              |
+-----------------------------------------------------+
| Foundation, AVFoundation, AppKit                     |
+-----------------------------------------------------+
```

Each engine module is a line-by-line port of the matching C++ module in
`src/`, which is itself a port of the Pascal units. `Swift/PORTING.md`
gives the rules that keep the two bit-identical; `docs/mapping-pascal-to-cpp.md`
maps Pascal symbols to their ports.

## Threads

| Thread | Owns |
|---|---|
| main | AppKit, all views, settings, the QSO log and score display |
| `mr-sim` | the `Contest` and every station; renders 512-sample blocks |
| Core Audio render thread | the `AVAudioSourceNode` render block |

## Hand-offs

- **GUI → simulation:** `SimulationThread.perform { contest in … }`
  queues a closure; the `mr-sim` thread runs queued commands between
  blocks. Settings changes travel the same way.
- **Simulation → audio:** `AudioBlockRing`, a fixed-size single-producer
  single-consumer ring of pre-allocated blocks. The render block only
  copies samples and advances an atomic index: no locks, no allocation,
  no Objective-C messaging. When the ring is full the producer parks on a
  semaphore and the consumer wakes it.
- **Simulation → GUI:** engine callbacks (`onQsoCompleted`,
  `onPlayerPieceFinished`, `onEndOfSession`) hop to the main thread with
  `postToMain`. A 30 Hz timer, running in the common run-loop modes so it
  keeps going while a menu is open, polls the clock and pile-up count.

## Why no `Synchronize`

The original Delphi code renders audio from a multimedia worker thread
that calls `Synchronize`, bouncing every buffer to the GUI thread before
the DSP runs. Under a heavy pile-up the UI and the audio compete. Here
the GUI thread never runs DSP; it only sends commands and shows results.

## Testing

- **Reference data:** `tools/golden/` runs the C++ engine with fixed seeds
  and writes keyer envelopes, filter outputs, scoring tables and six
  whole-contest traces into `Swift/Sources/MRTestSupport/Fixtures`. The
  Swift tests compare against them with `==`.
- **Unit tests:** one Swift Testing target per module (`swift test`),
  plus app-hosted tests in `Swift/App/Tests` that drive the window
  controller against a fake engine. Under tests the app never opens its
  window, starts audio or touches the real settings.
- **Threading:** `swift test --sanitize=thread` on MRAudio and
  MRSimulation.

## The C++/Qt port

`src/` holds the earlier C++/Qt 6 port. It is no longer the shipped app;
it stays as the reference engine for the golden data and for regression
checks against the Pascal behaviour.
